# 工程与设计维护规范

AGENTS.md 是日常开发规范入口，专项文档提供设计与架构细则。文档描述稳定边界与适用范围，类型、组件 CSS 与测试提供可执行的事实来源；调整规则时同时更新对应实现与验证。

## 设计依据

颜色参考 [Apple HIG Color](https://developer.apple.com/design/human-interface-guidelines/color) 的语义角色和浅 / 深色版本。平台系统色会随版本与环境变化；Electron 和网页的 CSS 色板是项目适配，不宣称具有 AppKit 的原生动态行为。

常态系统红直接采用当前 HIG 的浅色 `#FF383C`、深色 `#FF4245`，危险文字和实体按钮共用该色，不在组件内压暗。两端共用同一组令牌。默认鲜艳红是已确认的产品选择；在当前浅色背景上，小号红字和白字红按钮不满足 4.5:1，不宣称其达到普通文字 AA 对比度。

`prefers-contrast: more` 使用独立增强配对：白字填充采用 HIG 的 `#E9152D`，浅色小号红字采用按背景适配的 `#DC142B`，深色红字采用 HIG 的 `#FF6165`。这些实际配对由颜色回归检查约束。

普通文字与背景采用至少 4.5:1 的对比度目标；大文字、禁用与装饰性内容按各自条件判断。检查实际前景和背景，不能四舍五入后把未达标值算作通过。依据：[WCAG Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。颜色测试只覆盖声明的角色配对，不能证明完整页面合规。

模态遵循焦点进入、Tab 约束、背景不可交互、Esc 与关闭后焦点恢复，依据 [WAI-ARIA Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。命中区参考 [WCAG Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)，不能把图标墨迹当作点击区域。

圆角参考 [Apple WWDC25 设计说明](https://developer.apple.com/videos/play/wwdc2025/356/) 对固定矩形、胶囊和嵌套同心圆角的区分。客户端使用 CSS squircle 接近连续曲率的视觉方向；[MDN corner-shape](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/corner-shape) 定义的是 superellipse，并不承诺等同 AppKit 的原生曲线。该属性不继承，必须与组件半径一起维护；网页不依赖它，使用独立圆弧档位。比较同角色控件的切角程度与内缩，不按两端半径数值是否相等判断一致性。

按钮交互参考 [Apple HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) 的动作层级与输入方式反馈；细指针悬停反馈、触控命中区和禁用状态分开处理。等宽分组参考 [Apple 自定义布局示例](https://developer.apple.com/documentation/swiftui/composing-custom-layouts-with-swiftui) 按组内最宽内容测量并在受限空间重排的原则。项目的字数档、字号和高度由共享实现决定，不能表述为 Apple 强制的 CSS 尺寸。

动效参考 [Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)：用于明确反馈和上下文，动作简洁、与直接操作一致并可减少；按局部反馈、内容、步骤、弹层和直接操作分类，不把所有地方套一种转场。客户端优先，网页的 View Transitions 与触控布局按实际能力适配。

字号档位、间距、圆角、卡片默认几何和动效时长是产品选择，不存在唯一行业最佳数字。保留已确认的视觉方向，检查真实内容、放大文字、窄窗口和键盘；数值不合适时调整对应角色，不全站机械替换。

令牌按底层标尺、语义别名与组件几何分层，参考 [Design Tokens Format](https://www.designtokens.org/tr/2025.10/format/) 的分组与引用思想。现有 CSS 能表达关系时，不为格式一致额外引入生成器。

## 布局取舍

[Apple HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout) 强调内容分组、边线一致、控制与内容的关系，以及窗口和文字大小变化下的适应性；它没有为本项目的网页和 Electron 卡片规定统一像素宽度。采用这些原则，再根据真实字段、控件和阅读内容选择预算。旧值和参考产品截图都只能作为候选，不能直接成为规范。

| 角色           | 选择依据                                                                             | 接受的取舍                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 设置与账号卡片 | 两端都是单列的标签、说明和操作，不是宽表格；共享卡片上限，桌面外框额外包含页面内缩   | 减少标签到操作的空白距离；很长的名称仍单行省略，完整值通过 DOM 与悬停提示保留              |
| 认证列         | 相同字段无需按载体采用两种近似宽度；为密码尾部控件、验证码发送入口和错误文字预留空间 | 宽窗口增加外围留白，窄窗口让字段随容器收缩                                                 |
| 阅读列         | 按正文、代码与表格的混合内容选择较宽列，使用相对字号上限，正文与输入框共用边线       | 中文段落的行长比专用阅读器更长，以减少代码和表格的折行；窗口变窄时正常收缩                 |
| 编辑弹窗       | 单字段反馈和简短确认有明确内容边界；保留必要反馈与安全内缩                           | 长用户名在输入框内自然横向移动，不把名称编辑扩成宽面板                                     |
| 任务弹窗       | 正文复用认证字段预算，外框由正文和内缩推导；不按按钮旧定宽反推卡片                   | 验证、头像与简短确认采用同组等宽的紧凑动作；明确的全宽认证角色填满列。空间不足时收缩与重排 |
| 列表弹窗       | 比单字段编辑多出设备图标、两行信息、状态徽章和操作槽位                               | 保留较宽列表档，但不按条目数或最长名称无限加宽；条目数只影响滚动                           |

[WCAG 1.4.8 Visual Presentation](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html) 提到可调整至不超过 80 个字符、CJK 不超过 40 个字形的呈现机制。这是 AAA 条件，不能表述为 AA 强制默认宽度，也不能用一个 CSS 像素值证明整项合规。它提醒我们避免无限拉长段落，但 Velin 的聊天列还要承载代码和表格，不能把专用正文阅读器的窄列直接作为聊天默认。实际行长取决于字体、字号与混合内容；窄窗口继续允许自然重排。

调整宽度要同时比较段落行长、代码折行、控件空间和新增留白。检查默认与放大字号、短窗口、窄父容器和长文案；断点与内缩以令牌和组件 CSS 为事实来源。卡片上限与桌面外框必须区分，不能比较两者的数字后误判两端没有统一。

## 模块维护

- 类型与状态归所属领域，页面消费领域能力；持久化模块不反向依赖页面。共享模块只收纳跨端真实重复的纯协议与策略，不成为通用工具箱。
- 流程拆分围绕明确职责和测试边界，不按文件行数建立通用流程引擎。Hook 组合原则见 [React Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)，外部同步与派生值的区别见 [React useEffect](https://react.dev/reference/react/useEffect)。
- 异步列表区分账号作用域、读取顺序与写入占用。旧请求不能覆盖新结果，写入成功后刷新失败必须明确表达部分结果，不能恢复已知被删除的数据。
- 日志通过单一运行边界输出英文事件和白名单字段；不展开未知对象、请求正文或凭据。用户反馈由本地化显示边界提供。
- 新依赖或抽象要说明实际复杂度与收益；需求出现后再评估路由、虚拟列表或日志后端，不提前搭建未来框架。

## 规则与记录

新规则说明适用范围、问题证据、事实来源、例外与验证方法。lint 可以限制中文标识符与散落 console，命名是否准确、是否拼音、业务概念是否一致以及注释是否过时，仍需人工审查。

长期架构、设计与安全规范可以版本化。一次性改造过程、审查笔记、测试截图和验证流水保存在已忽略的本地目录，不放进维护文档；代码交付时直接报告实际执行结果与未验证范围。
